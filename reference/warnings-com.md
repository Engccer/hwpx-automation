# 주의사항: 한컴 COM 자동화

1. **HWPX 이미지 삽입은 XML 직접 편집 불가**: `<hp:pic>` 요소를 XML로 직접 구성하면 `hc:` 네임스페이스 참조 불일치로 **문서 손상** (한글에서 "손상된 파일" 오류). XSD 검증을 통과해도 한글이 열 때 실패함. 반드시 **한컴 COM `hwp.InsertPicture()`로 삽입** → XML 후처리로 위치/배치 조정
2. **양식 채우기 + 이미지 삽입 워크플로우**: (1) hwpx_edit.py로 셀 채우기 (2) XML 직접 편집으로 날짜/텍스트 수정 (3) COM으로 이미지 삽입 → HWPX 저장 (4) XML 후처리로 이미지 위치 조정 (5) COM으로 PDF 저장. 3~5단계를 **별도 Python 스크립트**로 분리 (COM segfault 방지)
3. **HWPX→PDF 변환**: `simple-hwp2pdf`는 실제로 MS Word COM 기반이라 HWPX 미지원. 한컴오피스 COM `hwp.SaveAs(path, 'PDF', '')`가 가장 확실
4. **COM은 Pandoc 생성 HWPX 본문을 인식하지 못함** (2026.4 확인): `hwpx_convert.py`(Pandoc)로 생성한 HWPX를 COM으로 열면 **본문 내용이 0자**로 읽힘. COM 저장 시 빈 문서로 덮어씌워 내용 전체 소실. `Visible=False`와 무관하며 사용자 개입과도 무관한 근본적 호환성 문제임.
   - **머리글(헤더) 편집 불가**: COM이 Pandoc HWPX의 secPr/header 구조를 인식 못해 `InsertHeaderFooter` 액션이 빈 머리글만 생성
   - **본문 인라인 삽입은 가능**: `MoveDocBegin` → `InsertPicture` → `BreakPara` → **별도 파일로 SaveAs** 시 내용+이미지 모두 보존됨 (2026.3.31 세션에서 확인, 2026.4.16 재현 성공)
   - **핵심**: 반드시 `SaveAs(다른파일, 'HWPX', '')`로 별도 파일에 저장해야 함. 같은 파일에 SaveAs하면 COM이 Pandoc 내용을 덮어씀
   - 한컴 COM 생성 HWPX(또는 한글에서 직접 저장한 HWPX)에는 이 문제 없음(Pandoc HWPX에만 해당)
5. **보안 모듈 DLL 경로 불일치로 팝업 무한 발생**: 레지스트리 `HKCU\SOFTWARE\HNC\HwpAutomation\Modules`의 `FilePathCheckerModule` 값이 가리키는 경로에 **실제 DLL이 있어야** `RegisterModule`이 유효하다. 경로만 등록되고 파일이 다른 위치에 있으면(프로젝트 이동·재설치 후 흔함) `RegisterModule`은 조용히 성공값을 반환하지만 실제로는 로드 실패해 보안 팝업이 매 Open/SaveAs마다 뜬다. 증상: 스크립트가 반복 멈춤. 진단: `reg query "HKCU\SOFTWARE\HNC\HwpAutomation\Modules"` + `ls <경로>` 둘 다 일치 확인. DLL은 `<repo>/vendor/FilePathCheckerModuleExample.dll`에 배치 (설치: `vendor/README.md`).
6. **COM 생성 HWPX는 양쪽 파이프라인에서 유효, 호환성은 단방향** (2026-06-10 검증): pyhwpx(COM)로 생성한 HWPX는 ① COM 재오픈 시 본문 전체가 정상으로 읽히고 ② hwpx-tomd(XML 파이프라인) 변환 시 단어·글자 recall 100%로 표 구조까지 보존된다. 즉 **COM 생성물 → XML 읽기·편집은 안전**하고, 금지 방향은 4번(Pandoc 생성물 → COM)뿐이다. 이 원칙에 따라 `hwpx_com.py`는 입력 파일을 절대 in-place로 덮어쓰지 않는다(별도 출력 파일 강제).
7. **pyhwpx `get_text_file()` 래퍼는 선택 블록만 추출** (2026-06-10 발견): 기본 시그니처가 `get_text_file(format='UNICODE', option='saveblock:true')`라서 **선택 영역이 없으면 None을 반환**한다. 전체 본문 추출은 저수준 COM을 직접 호출할 것: `hwp.hwp.GetTextFile("TEXT", "")` (option 빈 문자열). `hwpx_com.py --get-text`가 이 방식을 사용한다.
8. **암호화된 HWPX는 `SaveAs`만으로 암호가 유지됨**: `Open(path, 'HWPX', 'password:xxx')`로 연 뒤 `SaveAs(path, 'HWPX', '')`하면 원본 암호가 그대로 재적용돼 결과물이 다시 암호화된다. 반드시 `FilePasswordChange` 액션(`String=""`, `Ask=0`)을 먼저 실행해야 평문 HWPX가 나온다. 상세: `reference/encrypted-hwpx.md`
9. **연속 COM 호출 hang: 잔류 `Hwp.exe`** (2026-08-10 이슈 #3 관찰): COM 변환·저장을 연속 호출하면 두 번째 호출이 3분 이상 무응답한 사례가 있다. 잔류 `Hwp.exe`를 강제 종료한 뒤에는 정상 동작했다(원인 미확정, 잔류 프로세스 추정). 배치·연속 호출 전에는 잔류 프로세스를 확인하고 정리하라: `tasklist | findstr Hwp.exe` → **사용자가 한글로 문서를 열어 두지 않았는지 반드시 확인한 뒤** `taskkill /IM Hwp.exe /F` (미저장 문서가 있으면 소실됨). 2번(COM 단계를 별도 스크립트로 분리)과 같은 계열의 프로세스 수명 문제다.
10. **COM은 자기가 건드린 문단의 `<hp:linesegarray>`를 저장 시 아예 빼고 쓴다** (2026-08-12 한컴 13.0.0.3903 실측): 비가시 창(`XHwpWindows.Item(0).Visible = False`)으로 열어 `InsertPicture` 후 `SaveAs`하면, 그림이 들어간 문단만 레이아웃 캐시 없이 저장된다(나머지 문단의 캐시는 그대로). 그래서 **삽입 후 파일만 보고 그 문단의 줄 좌표(vertpos/vertsize)를 구하려는 코드는 100% 실패**한다. `hwpx_sign.py`의 floating 배치가 이 이유로 전면 실패했고, 다음 두 규칙으로 해결했다.
    - **좌표는 편집 전 원본에서 읽는다**: COM을 태우기 전에 `Contents/section0.xml`을 확보해 두고 앵커 문단의 lineseg를 거기서 읽는다. 부수 효과로 **그림 때문에 부풀지 않은 원래 줄 높이**를 얻어 "글자 줄에 겹쳐 찍기"에 더 맞는 좌표가 나온다.
    - **원본에도 캐시가 없으면 추정한다**: 문서 끝 문단이나 COM 네이티브 생성물(`hwpx_com.py --from-md`)은 마지막 문단에 캐시가 없다. 직전 줄에서 `다음 줄 vertpos = 직전 vertpos + vertsize + spacing`으로 추정한다(한컴 저장물 2종에서 정확히 일치). 추정을 쓴 경우 WARN을 남기고 PDF 육안 확인을 요구한다.
    - **주의**: 3번(lineseg를 **지워야** 한글이 연다)과 방향이 반대인 문제다. 읽을 때는 원본에서, 쓸 때는 변경 문단의 캐시를 지운다 — 둘 다 지켜야 한다.
11. **글상자·표 안의 lineseg는 개체 기준 상대좌표**: 공문 양식은 본문 전체가 글상자(`<hp:rect><hp:drawText>`) 하나인 경우가 흔하다. 그 안의 문단 lineseg `vertpos`/`horzpos`는 **글상자 기준**이라 `vertRelTo="PAPER"` 절대좌표에 그대로 더하면 위치가 크게 어긋난다(실측: 서명이 서명줄보다 100mm 위, 가로는 페이지 밖). `hwpx_sign.py`는 이 경우를 감지해 WARN을 내며, 보정은 `--horz-offset`/`--vert-adjust`로 한다(개체 기준 오프셋은 문서마다 상수라 한 번 맞추면 재사용 가능).
12. **한컴은 저장하면서 BinData 번호를 재부여한다**: 그림이 이미 있는 문서에 COM으로 그림을 넣으면, **새로 넣은 그림이 `image1`이 되고 원래 있던 그림이 `image2`로 밀린다**(2026-08-12 실측). 따라서 "원본에 없던 `binaryItemIDRef`가 새 그림"이라는 판별은 **정반대 결과**를 낸다. 실제로 그 판별을 쓰면 기존 그림을 서명으로 오인해 서명 크기로 줄여 서명줄로 옮기고, 진짜 서명은 인라인으로 방치한 채 `[OK]`를 낸다.
    - **판별 순서(hwpx_sign.py 구현)**: ① 삽입한 이미지 **파일명**이 `<hp:shapeComment>`의 "원본 그림의 이름:"에 남으므로 그것으로 찾는다 ② 실패 시 원본 앵커 문단의 자기 텍스트(앵커 제외)와 일치하는 문단의 그림 ③ 그래도 못 고르면 WARN 후 첫 그림.
    - **일반 규칙**: COM 왕복 후 개체를 다시 찾을 때 **ID·번호에 의존하지 말 것**. 파일명·주변 텍스트 같은 내용 기반 단서를 쓴다.
13. **문단 좌표는 스택으로 찾아야 한다**: `rfind("<hp:p")`로 앵커의 문단을 찾으면, 같은 문단 안에서 **이미 열렸다 닫힌 중첩 문단**(인라인 표의 셀)이 선택돼 셀 상대좌표를 종이 절대좌표로 쓴다. 여는/닫는 토큰을 스택으로 훑어 실제 포함관계를 만들고, 그 문단의 **자기 XML**(중첩 문단 구간을 도려낸 것)에서 lineseg를 읽어야 한다(중첩 셀의 linesegarray가 먼저 나오기 때문). 앵커 탐색도 원문 부분문자열이 아니라 태그를 벗긴 자기 텍스트로 해야 `(서명)`이 여러 `<hp:t>` 런으로 쪼개진 문서에서 동작하고, 머리글·꼬리말·각주 sublist는 COM의 본문 검색 대상이 아니므로 후보에서 제외한다.
14. **좌표를 신뢰할 수 없으면 성공을 반환하지 말 것**: 글상자·표 안 서명란은 자동 좌표가 종이 기준과 어긋나는데, 경고만 내고 `[OK]`·종료코드 0으로 끝내면 종료코드나 stdout을 보는 래퍼·에이전트가 인쇄 영역 밖에 서명이 찍힌 문서를 그대로 납품한다. `hwpx_sign.py`는 이 경우 `--horz-offset`/`--vert-adjust`가 **명시되지 않았으면 종료코드 1로 실패**하고 보정 방법을 안내한다(사용자가 좌표를 지정해 책임진 경우에만 통과).
